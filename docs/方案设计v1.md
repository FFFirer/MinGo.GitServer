# 极简 Git Server 自研方案：MVP 范围、架构决策与 Spec 开发计划

建议项目定位为 Minimal Git Forge：一个基于 ASP.NET Core 的轻量 Git 托管服务，专注仓库、分支、Tag、提交、文件浏览和在线编辑。

目标不是重新实现 Gitea，而是复用 Git 原生能力，开发最小的 Git 托管控制面和移动端 WebUI。

MVP 核心目标

从 WebUI 创建私有仓库，通过标准 Git 客户端 Clone/Push，再通过手机浏览器查看、编辑并提交文件，最终在本地 Pull 获取修改。

### 功能范围

| 模块 | MVP 必须实现 | 延后 |
| --- | --- | --- |
| Repository | 创建、列表、详情、删除 | Fork、迁移、镜像 |
| Git HTTP | Clone、Fetch、Push | Protocol v2 高级调优 |
| Git SSH | 暂不实现 | SSH Key、OpenSSH |
| Branch | 列表、创建、删除 | 分支保护、合并 |
| Tag | 列表、创建、删除轻量 Tag | 签名 Tag、Release |
| Commit | 历史、详情、Diff | Blame、Cherry-pick |
| Files | 目录树、查看、编辑、创建、删除 | 批量编辑、上传 |
| Web Commit | 单文件提交、乐观并发 | 多文件事务编辑 |
| Authentication | 单管理员、HTTPS Git 凭据 | OIDC、MFA、多角色 |
| WebUI | 桌面及移动端响应式 | PWA、离线编辑 |
| Operations | SQLite、日志、备份恢复 | HA、集群、队列 |

这里有一个关键决定：MVP 只做 Smart HTTP Git Transport，SSH 放到下一阶段。

这样能够减少 SSH 认证、密钥管理、命令授权和进程隔离的实现复杂度，同时保证标准 Git 客户端可用。

## 三、模块划分与接口设计

建议采用 模块化单体（Modular Monolith），而不是微服务。所有后端模块运行在一个 ASP.NET Core 进程内，但通过接口隔离 Git 引擎、业务规则和 HTTP 层。

### 3.1 后端模块

| 模块 | 核心职责 | 依赖 |
| --- | --- | --- |
| Identity | 管理员、Cookie 登录、Git Token | SQLite |
| Repository | 仓库元数据、创建、删除、访问权限 | SQLite + Git |
| GitTransport | Git Smart HTTP Clone/Fetch/Push | git-http-backend |
| GitReferences | Branch、Tag、HEAD | Git CLI |
| GitHistory | Commit、Tree、Blob、Diff | Git CLI |
| GitEditor | 文件修改、Tree 构造、Commit | Git plumbing |
| GitExecution | Git 进程、超时、并发、输出限制 | System.Diagnostics |
| Infrastructure | SQLite、配置、日志、备份辅助 | 文件系统 |

其中 `GitExecution` 是最重要的基础模块，其他业务模块不允许自行拼接命令行。

建议抽象以下接口：

csharp

```csharp
public interface IGitRepositoryStore
{
    Task CreateBareAsync(
        string repositoryPath,
        CancellationToken cancellationToken);
}

public interface IGitCommandRunner
{
    Task<GitCommandResult> ExecuteAsync(
        GitCommand command,
        CancellationToken cancellationToken);
}

public interface IGitReferenceService
{
    Task<IReadOnlyList<GitBranch>> ListBranchesAsync(
        Guid repositoryId,
        CancellationToken cancellationToken);
}

public interface IGitFileEditor
{
    Task<GitCommitResult> CommitFileAsync(
        CommitFileRequest request,
        CancellationToken cancellationToken);
}
```

`IGitCommandRunner` 应使用固定可执行文件、`ProcessStartInfo.ArgumentList`、禁用 Shell、限制环境变量，并为标准输出、标准错误和退出状态提供统一处理。

对于 Git HTTP 的流式进程执行，建议独立实现 `IGitTransportRunner`，不要强行使用会缓存全部输出的普通命令执行接口。

### 3.2 API 规划

REST API 统一使用 `/api/v1`，与 Git HTTP 协议路由隔离。

| Method | Endpoint | 功能 |
| --- | --- | --- |
| GET | `/api/v1/repos` | 仓库列表 |
| POST | `/api/v1/repos` | 创建仓库 |
| GET | `/api/v1/repos/{id}` | 仓库详情 |
| DELETE | `/api/v1/repos/{id}` | 删除仓库 |
| GET | `/api/v1/repos/{id}/branches` | 分支列表 |
| POST | `/api/v1/repos/{id}/branches` | 创建分支 |
| DELETE | `/api/v1/repos/{id}/branches/{name}` | 删除分支 |
| GET | `/api/v1/repos/{id}/tags` | Tag 列表 |
| POST | `/api/v1/repos/{id}/tags` | 创建 Tag |
| DELETE | `/api/v1/repos/{id}/tags/{name}` | 删除 Tag |
| GET | `/api/v1/repos/{id}/commits` | Commit 历史 |
| GET | `/api/v1/repos/{id}/commits/{sha}` | Commit 详情 |
| GET | `/api/v1/repos/{id}/diff` | Diff |
| GET | `/api/v1/repos/{id}/tree` | 文件树 |
| GET | `/api/v1/repos/{id}/blob` | 文件内容 |
| PUT | `/api/v1/repos/{id}/files` | 创建/修改文件并提交 |
| DELETE | `/api/v1/repos/{id}/files` | 删除文件并提交 |

分支名称、Tag 名称和文件路径都可能包含 `/`，不建议直接将它们作为单个路由段。上表中删除 Branch/Tag 的路由是逻辑表达，正式 OpenAPI 应改用明确的查询参数或请求体，并采用一致的 URL 编码规则。

Git 协议端点单独使用：

text

```text
/git/{owner}/{repo}.git/info/refs
/git/{owner}/{repo}.git/git-upload-pack
/git/{owner}/{repo}.git/git-receive-pack
```

Git Transport 不使用普通 JSON API 的返回格式，而是遵守 Git Smart HTTP 协议。

### 3.3 Git HTTP Gateway 的关键约束

这是 MVP 最需要提前验证的技术风险。

`git-http-backend` 是 CGI 风格程序，不是一个普通的 HTTP Server。ASP.NET Core 必须正确处理：

- CGI 环境变量，例如 `GIT_PROJECT_ROOT`、`PATH_INFO`、`REQUEST_METHOD`、`QUERY_STRING`、`CONTENT_TYPE`、`REMOTE_USER`。
- CGI 输出中的 `Status`、`Content-Type` 等响应头。
- 请求体与响应体双向流式转发，不能把整个 Pack 文件读入内存。
- 客户端断开连接时取消进程并回收资源。
- Git Upload-Pack 和 Receive-Pack 的不同授权规则。
- 通过可信认证上下文控制 Push，禁止匿名写入。
- 限制仓库路径、协议服务、请求大小和并发数。

第一阶段就应进行真实 `git clone`、`git push`、`git fetch` 的协议测试。 如果这个环节无法稳定工作，后面的 WebUI 开发没有意义。

## 四、数据模型设计

MVP 不需要复杂 ORM，也不需要将 Git 对象保存到 SQLite。

SQLite 元数据模型

Users

Id · Username · PasswordHash · IsAdmin · CreatedAt

Repositories

Id · OwnerId · Name · DefaultBranch · CreatedAt · DeletedAt

AccessTokens

Id · UserId · TokenHash · Scopes · ExpiresAt · RevokedAt

RepositoryPermissions

RepositoryId · UserId · Permission

AuditEvents

Id · ActorId · Action · RepositoryId · CreatedAt

Git Commit、Tree、Blob、Branch、Tag 等对象全部由 Bare Repository 保存，不在 SQLite 中重复建模。

即使 MVP 只有一个管理员，也建议保留 `UserId` 和 `RepositoryId` 的稳定标识，以避免以后从单用户迁移到双用户时重构仓库路径和权限模型。

删除仓库采用“先标记删除，再移动到隔离目录，最后清理”的方式，避免数据库事务成功但文件系统删除失败造成状态不一致。

### 6.2 Spec 编写规则

所有功能规格必须包含：

1. Goal：要解决什么问题。
2. In Scope / Out of Scope：功能边界。
3. Preconditions：执行前提。
4. Functional Requirements：使用 `FR-xxx` 编号。
5. Non-functional Requirements：使用 `NFR-xxx` 编号。
6. API Contracts：请求、响应、错误。
7. Security：认证、授权、输入验证。
8. Failure Handling：超时、冲突、异常回滚。
9. Acceptance Scenarios：Given / When / Then。
10. Dependencies：依赖模块与交付顺序。

以下是 Git 文件编辑模块的 Spec 示例。

SPEC-007：Web File Commit

示例

Goal：允许用户通过浏览器修改 Bare Repository 中的一个文本文件，并生成标准 Git Commit。

FR-001：支持创建、修改、删除单个文本文件。

FR-002：客户端必须提供目标 Branch 和预期 HEAD SHA。

FR-003：服务端必须检查仓库写权限。

FR-004：文件内容必须以 UTF-8 或明确指定的编码处理。

FR-005：提交必须使用 Git 标准对象和原子 Ref 更新。

FR-006：Branch HEAD 已变化时返回 `409 Conflict`，不得覆盖其他提交。

FR-007：成功后返回新 Commit SHA 和更新后的 Branch HEAD。

验收场景

Given：`main` 当前 HEAD 为 `A`。

When：用户修改 `README.md`，提交预期 HEAD `A`。

Then：产生 Commit `B`，其 Parent 为 `A`，且 `main` 指向 `B`。

When：另一个请求仍以 `A` 为基线提交。

Then：返回 `409 Conflict`，`main` 仍然指向 `B`。

这里建议把 Git Ref 的并发一致性作为不可妥协的要求，而不是在 MVP 后期补充。

### 6.3 API Contract 示例

yaml

```yaml

openapi: 3.1.0
info:
  title: Minimal Git Server API
  version: 0.1.0

paths:
  /api/v1/repos/{repositoryId}/files:
    put:
      operationId: commitFile
      summary: Commit a single file change
      parameters:
        - name: repositoryId
          in: path
          required: true
          schema:
            type: string
            format: uuid
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CommitFileRequest'
      responses:
        '200':
          description: Commit created
        '401':
          description: Authentication required
        '403':
          description: Write permission denied
        '409':
          description: Branch HEAD conflict
        '422':
          description: Invalid file or reference
        '413':
          description: File exceeds size limit

components:
  schemas:
    CommitFileRequest:
      type: object
      required:
        - branch
        - path
        - expectedHead
        - content
        - message
      properties:
        branch:
          type: string
        path:
          type: string
        expectedHead:
          type: string
        content:
          type: string
        message:
          type: string
```

实际实现中还需要补全响应 Schema、认证要求和字段长度约束。建议将 OpenAPI 作为前后端之间唯一的 API Contract 来源，TypeScript Client 由构建流程生成，不手写重复类型。

## 七、分阶段开发计划

采用 7 个阶段，先解决 Git 协议与安全，再完成 WebUI。以下是工程工作量估算，不代表自然日工期。

1. P0 — 工程骨架与基准环境
   预计 1～2 工程日
   建立 Solution、模块结构、SQLite Migration、OpenAPI、Vite、测试工程、Podman Compose。
   验收： API 和前端可独立启动，容器健康检查正常，空闲内存基准可采集。
2. P1 — Git Engine 与 Bare Repository
   预计 2～3 工程日
   实现 Git CLI Runner、仓库初始化、仓库路径隔离、命令超时、输出限制和进程回收。
   验收： 可以创建 Bare Repo，读取 HEAD、Branch、Tag 和 Commit；恶意路径无法逃逸仓库根目录。
3. P2 — Git Smart HTTP
   预计 3～5 工程日
   集成 `git-http-backend`，完成流式 Clone/Fetch/Push、认证授权和 Git Token。
   验收： 标准 Git CLI 可以完成 Clone → Commit → Push → Clone；匿名 Push 被拒绝；大文件传输不会完整缓存在 ASP.NET Core 内存中。
4. P3 — Git 查询与仓库管理 API
   预计 3～4 工程日
   实现仓库 CRUD、Branch、Tag、Commit、Diff、Tree、Blob 查询。
   验收： API 返回结果与 Git CLI 一致；不存在跨仓库访问；分页和内容大小限制生效。
5. P4 — Web Commit Engine
   预计 3～5 工程日
   实现单文件创建、修改、删除、Commit Tree、原子更新 Ref、冲突检测。
   验收： 浏览器修改可以被 Git CLI Pull；并发修改返回 409；失败时不留下被错误引用的 Commit。
6. P5 — Responsive WebUI
   预计 5～8 工程日
   完成登录、仓库列表、文件浏览、Branch/Tag、Commit/Diff、CodeMirror 文件编辑。
   验收： 375px 手机视口下完成创建仓库、编辑文件、提交、查看历史；无关键操作需要右键或 Hover。
7. P6 — 安全、性能、部署与恢复
   预计 3～5 工程日
   完成安全测试、资源压力测试、备份恢复、容器限制、日志和部署文档。
   验收： 2C / 2GB 环境中完整闭环稳定，备份可恢复，异常 Git 进程可回收，资源指标达到目标。

## 十、首批应编写的 Spec

正式开发前，建议先完成以下四份规格：

| 优先级 | Spec | 必须回答的问题 |
| --- | --- | --- |
| P0 | `000-product/scope.md` | MVP 具体包含什么、不包含什么 |

| P0 | `002-git-engine/spec.md` | Git CLI 如何安全执行、限制并发和处理失败 |
| P0 | `003-git-http/spec.md` | CGI 流式代理、Clone/Push 和认证如何实现 |

随后按照开发阶段逐步补齐 Repository、References、History、Editor、WebUI 和 Operations 的 Spec。

最关键的开发原则：每个阶段必须交付一个可以独立验证的结果，而不是先写完所有模块再进行集成。

其中 P2 的 Git Smart HTTP 和 P4 的 Web Commit Engine 是两个核心技术风险点，应尽早验证。只要这两项成立，剩余工作主要是常规 ASP.NET Core API 和前端工程开发。

最终建议以 P0～P4 作为后端最小闭环，P5 作为完整产品闭环，P6 作为可部署验收门槛。这样即使中途调整 UI 技术路线，也不会影响底层 Git 托管能力。
